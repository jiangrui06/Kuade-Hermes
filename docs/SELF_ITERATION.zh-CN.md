## 模块边界

| 模块 | 责任 |
| --- | --- |
| `iteration/source.ts` | 复制明确的源码目录、记录指纹和原始测试，排除构建产物、环境文件及运行数据 |
| `iteration/service.ts` | 创建标准 Harness 任务，记录状态，等待任务结束及其他任务空闲 |
| `iteration/process.ts`、`verify.ts` | 依据真实退出码运行依赖安装、类型检查、原始测试、构建和 electron-builder |
| `iteration/artifact.ts`、`handoff.ts` | 验证 EXE 与应用资源指纹，启动新版本，健康检查失败时尝试回退 |
| `main/boot-health.ts`、`active-version.ts` | 当前进程、版本、用户目录与本轮回执绑定；旧入口跳转到已验收版本 |
| `renderer/features/Iteration.tsx` | 启动、进度、停止、查看任务、重试验证 |

原始测试与构建脚本单独保存，任务结束后重新校验指纹。候选副本修改测试脚本或删除测试，不会绕过原始验证门槛；新增和修改的候选测试也会运行。模型结束文本不构成通过证据。

## 更新与恢复

当前源码新增独立启动门槛：electron-builder 将候选输出到每轮的 `application/win-unpacked`，与 `source` 并列；祖先目录含 `node_modules` 时拒绝验证。基线保存并校验 `scripts/check-packaged-startup.mjs`，候选中的同名文件被修改也不会替换该检查。打包后用现成的 Playwright Electron API 启动独立、无凭据的临时用户目录，核对界面、应用版本、引擎状态、会话／模型设置 RPC 及随包原生组件路径，再关闭该检查实例。`packaged-startup` 以真实退出码计入第七道验证；失败不生成可切换产物，旧程序继续运行。原有正式切换与回退健康检查仍保留。

该改进来自 0.1.7 解压验收发现的依赖借用问题：构建目录内的程序可能从上级源码依赖中补齐漏包，因此打包成功与源码目录内启动均不足以证明独立可用。源码已修复并验证完整包通过、缺依赖包被拒绝；已交付的 0.1.7 安装包不因本地源码变化而自动更新。新门槛的完整自迭代验证另行记录。

实现依据：[electron-builder 配置与输出目录](https://www.electron.build/docs/configuration/)、[Playwright ElectronApplication](https://playwright.dev/docs/api/class-electronapplication)。

当前实现针对 Windows x64 的独立版本目录。沿用 Electron 和 electron-builder 产物，不覆盖正在运行的程序。外部守护进程先就绪，旧程序退出后启动候选；只有渲染界面确认加载、Harness 引擎就绪且进程持续存活，才发布当前版本指针。启动失败时关闭本轮候选进程，恢复旧版本。旧版本也启动失败时记录失败，保留两份程序。

用户数据目录保持一致；源码副本不携带模型 Key 与会话。成功后的候选源码作为下一轮起点。便携版旧入口可跳转到已验证的新版本。NSIS 安装目录替换、安装版更新和 macOS 更新另行开发验收。

需要可用的 Node.js 22+、npm 与构建网络，开始前检查至少 3 GiB 可用空间。随应用提供的电脑控制二进制只有在源码与指纹一致时复用；修改原生组件需要 Go。磁盘需求随依赖与版本数量增长，历史候选不会自动删除。
