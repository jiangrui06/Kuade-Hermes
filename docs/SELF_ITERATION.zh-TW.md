在「自我迭代」選擇與目前應用程式版本一致的 Kuade 原始碼目錄，填寫具體改進需求，沿用工作台選取的模型與思考設定。宿主建立獨立副本、增加修補版本，再交由 Harness 執行。任何頁面按 Ctrl+Shift+I 直接進入「自我迭代」；Ctrl+N 新建工作的行為維持不變。驗證失敗保留副本、工作與日誌，可繼續工作後重新驗證。

## 模組

- `source.ts`：複製明確的原始碼目錄並記錄指紋與原始測試，排除建置產物、環境檔案和執行資料。
- `service.ts`：建立標準 Harness 工作，維護狀態，等待工作結束及其他工作閒置。
- `process.ts`、`verify.ts`：依實際退出碼執行依賴安裝、型別檢查、原始測試、建置和 electron-builder。
- `artifact.ts`、`handoff.ts`：驗證 EXE 和應用程式資源指紋，啟動新版，健康檢查失敗時嘗試回退。
- `boot-health.ts`、`active-version.ts`：綁定程序、版本、使用者目錄與本輪回執；舊入口跳轉至已驗收版本。
- `Iteration.tsx`：啟動、進度、停止、檢視工作及重試驗證。

原始測試與建置腳本獨立保存並核對指紋；候選刪除測試或修改腳本不會繞過基線。新增及修改的候選測試也會執行。模型完成文字不構成驗收證據。

## 更新與恢復

目前原始碼新增獨立啟動門檻：electron-builder 將候選輸出至每輪的 `application/win-unpacked`，與 `source` 並列；祖先目錄含 `node_modules` 時拒絕驗證。基線保存並核對 `scripts/check-packaged-startup.mjs`，候選內的同名檔案即使被修改，也不會取代檢查。打包後使用既有 Playwright Electron API，以獨立、無憑據的臨時使用者目錄啟動，核對介面、版本、引擎狀態、會話／模型設定 RPC 及隨包原生元件路徑，再關閉檢查實例。`packaged-startup` 依實際退出碼作為第七道驗證；失敗不產生可切換產物，舊程式繼續執行。正式切換與回退健康檢查維持不變。

這項改進來自 0.1.7 解壓驗收發現的依賴借用問題：建置目錄中的程式可能從上層原始碼依賴補齊漏包，因此打包成功及原始碼目錄內啟動皆不足以證明獨立可用。已驗證完整包通過、缺依賴包被拒絕；已交付的 0.1.7 安裝包不會隨本機原始碼變更而自動更新。新門檻的完整自我迭代驗證另行記錄。

實作依據：[electron-builder 設定與輸出目錄](https://www.electron.build/docs/configuration/)、[Playwright ElectronApplication](https://playwright.dev/docs/api/class-electronapplication)。

目前支援 Windows x64 獨立版本目錄，沿用 Electron 和 electron-builder，保留正在執行的舊程式。外部守護程序就緒後，舊版退出並啟動候選；介面載入、Harness 引擎就緒且程序持續存活才發布版本指標。失敗時關閉本輪候選並啟動舊版；回退也失敗則保留兩版及診斷。

使用者資料目錄保持一致，原始碼副本不攜帶金鑰或對話。成功後以候選原始碼作為下一輪起點；可攜版舊入口會跳轉至已驗證新版。NSIS 安裝目錄替換、安裝版與 macOS 更新另行驗收。

需要 Node.js 22+、npm、建置網路及至少 3 GiB 可用空間。電腦控制二進位只有在來源與指紋一致時沿用；修改原生元件需要 Go。磁碟需求隨依賴和版本數成長，歷史候選不會自動刪除。
